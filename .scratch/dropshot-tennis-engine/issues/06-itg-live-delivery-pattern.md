# 06 — How does the ITG live-model pattern work, and what must a tennis model export to slot in?

Type: research
Status: resolved

## Question

Delivery is decided: the ITG site, copying the existing live pattern. But the pattern needs to be understood precisely before the model is designed, because it constrains what the model may be — a Cloudflare Worker cannot run R, and a model that only exists as a fitted R object cannot be served.

Read the actual code in `C:\dev\inthegame-blog` and establish:

1. **The Worker.** What `worker/src/ep-model.js`, `wp-model.js` and `live-wp-calibration.js` actually do — how a model gets from training into JavaScript, what format the exported model takes (the survey suggests XGBoost exported to JSON via `_xgb-runtime.js`), and how large those artifacts are.
2. **The live loop.** How `live-poller.js` and `live-badge.js` work — what they poll, at what interval, how state flows from the feed into the model and out to the page, and how failures are handled mid-match.
3. **The static path.** How the Quarto site reads parquet from Cloudflare R2 via `hyparquet`, and how each verse's `build-blog-data.yml` populates R2. This is the route for the rankings and GOAT pages.
4. **UX Invariant 3** in `inthegame-blog/CLAUDE.md` — "any probability/scenario display must recompute from live state, not just static parquet". Establish exactly what this demands of a new model.
5. **The constraint that matters most.** Given the Worker is JavaScript: can our two-speed design work, where the slow Bayesian layer produces per-player posterior parameters as a small JSON blob, and the fast layer is a closed-form tennis Markov recursion implemented directly in JS? Assess whether that closed form is cheap enough to run per-point in a Worker. If so, we need **no** ML runtime in the browser at all — a materially simpler path than the XGBoost route football uses.
6. **Registration.** What must be added for a new sport to appear — routes, config, build workflow, nav.

**Deliverable:** a concrete integration spec — the file(s) a tennis model must produce, their format and size budget, where they go, and what changes in `inthegame-blog`. Flag anything in the existing pattern that assumes a sport-with-a-clock and won't transfer to tennis's point/game/set structure.

## Answer

All findings below are from reading actual files in `C:\dev\inthegame-blog` (paths and line numbers as of 2026-08-27), not from the survey or memory. No files in that repo were modified.

### 1. The Worker — how a model gets from R into JS, and what the artifact actually is

`worker/src/ep-model.js` (AFL Expected-Points) and `worker/src/wp-model.js` (AFL + football Win-Probability, xG, EPV) are XGBoost tree-walkers. The shared engine lives in `worker/src/_xgb-runtime.js`:

- `flattenTree(node)` converts XGBoost's nested `xgb.dump(dump_format="json")` tree into a flat array indexed by `nodeid`, so `walkTree` is O(1) array lookups instead of tree traversal.
- `flattenRawTree(rawTree, featureNames)` does the same for the newer `xgb.save.raw()` parallel-array export format panna moved to on 2026-07-20 (parity/precision reasons documented at length in that file — float32 threshold comparisons, `Math.fround` on both feature and threshold sides).
- `walkTree(tree, features)` walks one tree in ≤200 steps, following `yes`/`no`/`missing` branches by comparing `features[node.split] < node.threshold`.
- `predictEP`/`predictWp` sum every tree's leaf value (round-robin by class for EP's `multi:softprob`; single-sum + sigmoid/clamp for WP), i.e. softmax or sigmoid over raw logits — a handful of arithmetic lines *after* the tree walk, which is the expensive part.
- `makeModelLoader(build)` gives every model module-scope caching: fetch once per Worker isolate, in-flight de-dup so N concurrent cold-start requests trigger one R2 fetch, never re-fetch after that.

**The model artifact is a JSON blob living in the R2 bucket `inthegame-data`**, fetched via `env.R2.get(key)` (e.g. `afl/ep-model-live.json`, `afl/wp-model-chain.json`, `football/wp-model.json`, `football/xg-model.json`, `football/epv-model.json`, `football/xgot-model.json`). Concrete sizing evidence found: `docs/reference/models/afl-wp-models.md:199` states the live AFL WP model (`afl/wp-model-chain.json`) is `binary:logistic`, `max_depth=4`, **152 trees**, 5 features (`margin, period, period_seconds, game_seconds, home`). At depth 4 each tree has ≤15 internal + 16 leaf nodes; 152 trees × ~30 nodes × the JSON dump's per-node fields (`nodeid, split, split_condition, yes, no, missing, children` or `leaf`) puts this file in the tens-to-low-hundreds-of-KB range uncompressed — I could not fetch the live R2 object to get an exact byte count (out of scope: read-only local-code task, no `wrangler r2 object get --remote` run), but the shape (152 shallow trees, 5 features) is verified straight off the docs, not estimated from nothing. AFL EP (`afl/ep-model-live.json`) is bigger: `max_depth=6`, `num_class=5`, 14 features (`docs/reference/models/afl-ep-model.md:53`) — deeper, more classes, more trees than WP.

**Publishing is manual/pipeline-triggered, not part of the automated blog-data GHA.** `torpdata/.github/workflows/build-blog-data.yml` uploads only `blog/*.parquet` files to R2 (`wrangler r2 object put "inthegame-data/afl/$(basename $f)" --remote`, line 336-352) — it never touches `ep-model-live.json` or `wp-model-chain.json`. Confirmed in `torpverse/docs/plans/LIVE-WP-CALIBRATION-PLAN.md:55-58`: "The worker serves model JSON from R2, not GitHub releases... uploaded via `wrangler r2 object put` (done 2026-07-22; **future refits must repeat this step**)" — i.e. it's a one-off manual/scripted step run by whoever refits the model, not a CI job. This matters for tennis: publishing a new posterior-parameter blob is a `wrangler r2 object put tennis/<key>.json --remote` call from wherever the Bayesian layer runs (R, Python, whatever), same as torp does today, with no new CI infrastructure required.

**`worker/src/live-wp-calibration.js` is the closest existing precedent to the proposed tennis design**, and it is *not* an XGBoost model — it's exactly the "small JSON blob + closed-form arithmetic" shape the ticket is asking about:
- The R2 object (`afl/live-wp-calibration.json`) is 5 scalars: `{form, a, b, c, ramp_mins, margin_cap}`.
- `applyLiveWpCalibration()` is ~6 lines: clamp, `logit`, a leverage weight (`liveWpLeverageWeight`, 2 lines of arithmetic), then `a + (b + c*w) * logit(p)` through a sigmoid.
- Same module-scope cache pattern as the XGBoost loaders (`_calibCache`/`_loadingCache` Maps), same R2-fetch-once-per-isolate discipline.
- **Hard rule enforced in code**: identity fallback (return input unchanged) on *any* failure — missing R2 object, malformed JSON, unrecognized `form`, non-finite coefficients — never throw, because a transient calibration-fetch blip must not take down live scoring. This is the fallback contract a tennis engine's parameter blob should copy exactly.

Conclusion for Q1/Q5: **the Worker's actual contract is "fetch a small JSON object from R2 once per isolate, run some JS arithmetic on it per request" — XGBoost tree-walking is just the specific arithmetic `ep-model.js`/`wp-model.js` happen to implement, not a constraint the platform imposes.** `live-wp-calibration.js` already proves a non-ML, few-scalar, closed-form JSON+arithmetic model runs in this Worker in production today. A tennis Markov recursion is architecturally identical to `live-wp-calibration.js`, just: (a) the JSON blob carries per-player serve/return parameters instead of 5 global calibration scalars, and (b) the "arithmetic" is a point→game→set→match recursion instead of a sigmoid.

**Cost comparison, concretely**: predicting one WP number today means walking 152 trees × ~4 branch comparisons = ~600 comparisons, and that's the *cheap* AFL WP model — it happens for every relevant chain row (thousands of rows across a match, e.g. EP scores every EPV-relevant event, hundreds per match). A tennis point-by-point Markov recursion (serve-point win prob → game win prob via a closed-form or ~7-state DP → set win prob via a ~7×7 game-score grid + tiebreak state → match win prob via best-of-3/5 set combinatorics) is on the order of a few hundred floating-point operations **total per call**, and — critically — it only needs to be evaluated once per poll tick (every 15-30s per live match, see §2), not once per historical row. This is cheaper than what's already shipping in production for two sports. **The closed-form path is not just viable, it is strictly cheaper than the existing XGBoost route**, and needs zero ML runtime (no tree format, no feature-vector marshalling, no `EXPECTED_FEATURES` drift-detection machinery) in either the Worker or the browser.

### 2. The live loop — `live-poller.js` / `live-badge.js`

`live-poller.js` (root-level, shared by every sport) is **already fully sport-agnostic** — this is good news for tennis, zero changes needed to this file:
- `window.createLivePoller({ sport, scoreInterval, waitingInterval, heartbeatInterval, isGameLive, isImminentGame, extractSnapshot, snapshotKey, snapshotDedup })` — every sport-specific bit is an injected callback.
- It polls `WORKER_BASE_URL + sport + "/live-scores?_t=..."` (e.g. `.../tennis/live-scores`) with `cache:"no-store"`.
- Cadence states: `live` (default 30s, config `scoreInterval`) while `isGameLive` is true for any game; `imminent` (default 60s) when a game starts soon; `heartbeat` (default 5min) when nothing's on radar; `backoff` (60s) after 5 consecutive fetch failures, recovering after 3 consecutive successes.
- Handles tab visibility (pauses polling when hidden, resumes with a sensible cadence guess on visible), a 15s fetch timeout, an AbortController so `stop()` actually cancels in-flight fetches, and generation-token guards against start/stop races.
- Failure handling: a non-2xx or malformed body increments a fail counter and eventually backs off to the slow cadence; the poller never fully stops itself (a `stopWhen` callback lets a *page* opt out once its tracked match is over, but the engine itself keeps a heartbeat forever so a page open hours before kickoff still sees the game start).

`live-badge.js` (root-level, `window.liveSimBadge.create(opts)`) is also sport-agnostic by design: `create({ prefix, fallbackText, replayText })` returns a `badge(meta)` renderer; only the CSS class prefix and two text-formatting callbacks are sport-specific, everything else (state resolution order: fallback → replay → feed-unavailable → live → idle; degradation-flag composition) is shared. A tennis instance would be `window.liveSimBadge.create({ prefix: "ts" })` with no changes to the file.

**Data flow, feed → model → page**: the Worker's `/{sport}/live-scores` endpoint returns `{updated, games:[...]}`; `live-poller.js`'s `onScoreUpdate(games, data)` callback (page-supplied) is where the page-side model gets invoked per tick. For a Worker-scored model (AFL/football's XGBoost path), the *Worker* has already attached `wp`/`ep`/`equity` fields onto event rows before the page ever sees them (via `/football/live-events/{id}` or `/afl/live-chains/{id}`, separate endpoints from `live-scores`, fetched by the match page directly, not by the generic poller). For a page-scored model (AFL/football's own browser win-prob, `afl/win-prob.js`/`football/win-prob.js`), the poller just delivers raw score/clock state and the page computes probabilities client-side from parquet-sourced coefficients. **Both shapes are available to tennis**: either the Worker runs the Markov recursion server-side on live score-state and exposes `wp`/`p_win` fields on its own `/tennis/live-events/{id}`-style endpoint, or the browser runs the identical recursion client-side once it has the per-player parameter blob + live score-state from the poller. Given the recursion's near-zero cost, doing it **in the browser** (avoiding a round-trip per point) is plausible and arguably preferable — but either placement is supported by the existing plumbing.

### 3. The static path — parquet via R2/hyparquet, and `build-blog-data.yml`

Confirmed from `CLAUDE.md`: each sport has its own `*data` repo (`torpdata`, `pannadata`, `bouncerdata`) whose `build-blog-data.yml` GHA workflow downloads source parquet from that sport's GitHub Releases (the `piggyback`/release-as-data-bus pattern), aggregates via an R script, and uploads the results to the shared R2 bucket `inthegame-data` under a sport-prefixed key (`afl/ratings.parquet`, `football/predictions.parquet`, etc.) via `wrangler r2 object put --remote` — verified directly in `torpdata/.github/workflows/build-blog-data.yml:316-353`. The blog reads these via `hyparquet` (pure-JS, CDN-loaded) in OJS cells, never touching R at render time. `execute: freeze: auto` in `_quarto.yml` means Quarto itself needs no R dependency.

**For tennis this is the path for rankings/GOAT/career pages** (static, refreshed on whatever cadence the Bayesian layer refits) — a new `dropshot`-nicknamed data repo (or reuse of an existing one) would need its own `build-blog-data.yml` uploading `tennis/ratings.parquet`, `tennis/rankings.parquet`, etc. to R2, exactly mirroring torpdata/pannadata/bouncerdata. This is a **separate artifact from the live-model parameter blob** (§5below) — parquet for static/aggregate display, the small JSON blob for the live Markov recursion's per-player inputs.

### 4. UX Invariant 3 — what it demands of a new model

`CLAUDE.md`'s UX Invariant 3 (verbatim): *"Every probability/scenario/table display must track live match state. Any number derived from simulation or enumeration... must consume `wcLiveSim` streams (or the sport's live equivalent) so it recomputes from in-progress scores AND locks finished results — the static `wc2026_*` parquets are fallback only."* It's reinforced by `docs/reference/MODELS.md`'s standing principle: *"Every live in-game number... must come from an XGBoost model scored LIVE... never a pre-stored parquet column."*

Read literally, that second sentence says "XGBoost" — but the actual enforced behavior (per §1's evidence) is "scored live from current state," not "must specifically be a gradient-boosted tree." `live-wp-calibration.js` already isn't XGBoost and still satisfies the intent. **What Invariant 3 actually demands of a tennis model**: any win-probability/scenario number shown while a match is live must be recomputed from the live score-state on every update — not read off a pre-computed parquet column, not "correct only at match end." The closed-form Markov recursion satisfies this *more cleanly* than the XGBoost route: since it's cheap to evaluate, it can be run fresh on literally every poll tick or every point, with no caching-staleness risk at all — there's no "trained model artifact might be behind current form" ambiguity the way a periodically-retrained XGBoost model has, only "are the per-player serve/return parameters current," which is the slow Bayesian layer's freshness question, orthogonal to per-point recomputation. **Flag for whoever writes `MODELS.md`'s eventual tennis row**: its wording literally says "XGBoost model" as the standing principle; a tennis row should either footnote that the principle's *actual* requirement is "live-scored, not parquet-cached" (proven by the calibration sidecar precedent) or the doc's phrasing should be loosened when tennis lands, so a future reader doesn't think tennis is out of compliance for using a non-ML closed form.

### 5. The two-speed design — is it supported? (the question that matters most)

**Yes, cleanly, and it is the *smaller* lift compared to the XGBoost route.** Concrete integration spec:

**Slow layer (Bayesian, offline, wherever it runs — R matches the rest of the ecosystem's convention)**: fits per-player serve/return posterior parameters (e.g. `p_1st_in`, `p_win_1st_serve`, `p_win_2nd_serve`, `p_win_return_1st`, `p_win_return_2nd`, or whatever the model spec (ticket 08) lands on), exports one JSON object per player (or one JSON blob keyed by player id, matching the calibration-sidecar's flat-object convention rather than nesting).

**Artifact shape** (mirrors `live-wp-calibration.json`'s conventions exactly — versioned `form` string + flat numeric fields, so the Worker's loader can apply the same `SUPPORTED_FORMS` allow-list / identity-fallback pattern):
```json
{
  "form": "serve_return_markov_v1",
  "as_of": "2026-08-27",
  "players": {
    "player_id_123": { "p_1st_in": 0.62, "p_win_1st": 0.74, "p_win_2nd": 0.51 },
    "player_id_456": { "p_1st_in": 0.58, "p_win_1st": 0.71, "p_win_2nd": 0.49 }
  }
}
```
**Size budget**: ~5-10 scalars per player. Even a full ATP+WTA active-player slate (a few thousand players) at ~10 numbers each is low hundreds of KB as one JSON file — smaller than a single AFL WP model (152 trees) and dramatically smaller than the EP model (depth-6, 5-class). A single live match only needs its two players' rows, so the Worker/browser could equally fetch a tiny per-match blob (`tennis/live-params/{matchId}.json`, a few hundred bytes) instead of the whole-slate file, whichever the rest of the pipeline finds more convenient to publish.

**Fast layer (JS, per point, wherever it's placed — Worker or browser, both work per §2)**: given `{p_1st_in, p_win_1st, p_win_2nd}` for server and returner, compute:
1. `p_win_serve_point` (weighted by 1st/2nd serve split) — a few lines.
2. `p_win_game(p_win_serve_point)` — closed-form geometric-series formula for a single game from deuce, or a tiny recursive/tabulated DP over the 0-40/deuce/ad states (≤20 states) — well under 100 arithmetic ops.
3. `p_win_set(p_win_game_server, p_win_game_returner)` — DP over the game-score grid (0-0 through 6-6 + tiebreak state, ~50 states) using the score-to-win recursion — a few hundred ops, computed once and reusable as a lookup table if desired.
4. `p_win_match` — combinatorial sum over best-of-3/5 set outcomes using `p_win_set` — trivial.

All of this is "about 50 lines of arithmetic," exactly as the ticket estimated, and is **cheaper per call than a single XGBoost tree walk of the existing AFL/football models**, let alone cheaper than doing that walk on every row of a match. Running it fresh per point (or per poll tick, whichever cadence is chosen) comfortably fits inside a Cloudflare Worker's CPU budget — nowhere close to the limits that `nodejs_compat`/WASM-heavy work like `og.js`'s satori rendering has to worry about.

**Conclusion: no ML runtime (no XGBoost, no ONNX, no tree JSON, no `_xgb-runtime.js`-equivalent) is needed anywhere in this pattern for tennis.** The only shared infrastructure worth reusing is the *generic* parts: the R2-fetch-once-per-isolate module-scope cache (`makeModelLoader`'s pattern, or a hand-rolled version like `live-wp-calibration.js`'s `_calibCache`/`_loadingCache` Maps), the identity/never-throw fallback discipline, and `live-poller.js`/`live-badge.js` unchanged. A new `worker/src/tennis-engine.js` (or under whatever nickname the dropshot verse gets) implementing the recursion directly, with its own small JSON loader function, is the entire new Worker surface area — no analog of `ep-model.js`'s tree-flattening or `wp-model.js`'s `EXPECTED_FEATURES_*` drift-detection is needed, because there's no trained tree structure whose shape can silently drift; the only "drift" risk is the parameter blob's `form` field changing shape, which the calibration sidecar's validate-and-fall-back-to-identity pattern already handles.

### 6. Registration — what a new sport needs

From `worker/src/index.js`'s router (`export default { fetch... }`, lines ~2700-2756) and `_quarto.yml`:

- **Worker routes**: add `if (path === "/tennis/live-scores") return handleTennisLiveScores(request, env)` and any per-match endpoint (`if (path.startsWith("/tennis/live-events/")) ...`) to the plain if-chain in the router's `fetch()` — there is no route-table/framework abstraction to register with, it's literally a sequence of `path.startsWith`/`path ===` checks. Decide whether tennis's live-events endpoint needs `needsAllowlist` origin-gating (only relevant if the upstream feed is rate-limited/authenticated the way Opta/AFL CFS are).
- **`wrangler.toml`**: no changes needed for the R2 binding or D1 (both are shared, sport-agnostic bindings already declared once). A new **cron trigger** would only be needed for a scheduled live-feed refresh job, and the file's comment notes **5 of 5 free-tier cron slots are already used** — a tennis live-refresh cron would need to either replace/consolidate an existing slot or dispatch off an existing cron's time window (same pattern `handleScheduled`'s dispatcher already uses to route multiple logical jobs off one cron string).
- **Quarto site**: a new `tennis/` (or verse-nickname) directory of `.qmd` pages mirroring `afl/`/`football/`'s layout, its own `tennis/CLAUDE.md` per the repo's per-sport-doc convention, and a new navbar block in `_quarto.yml`'s `navbar:` list (`_quarto.yml`'s navbar is the documented SSOT for the live page list). Follow the **Page Rename Checklist** (`_quarto.yml` navbar + `_redirects` + `_headers`) for any new page/JS resource.
- **Beta/soft-launch option already precedented**: cricket ships exactly the "source exists, not live" pattern tennis will likely want at first — `_quarto.yml` render-excludes `cricket/**` and comments out its navbar entry until it's ready (`CLAUDE.md`'s Architecture section). Tennis can land the same way: pages and worker code merged and working, excluded from the public build/nav until the live pattern is validated end-to-end.
- **Docs**: add a tennis section to `docs/reference/MODELS.md` (see the flag in §4 about its "XGBoost" wording), and register the new data repo's parquet outputs in `CLAUDE.md`'s "Data tables" table (`{sport}: parquet files` row) the same way `torpdata`/`pannadata`/`bouncerdata` are listed.
- **`live-poller.js`/`live-badge.js`**: zero code changes — instantiate with `sport: "tennis"` / `prefix: "ts"` config objects from tennis's own page-level JS, per §2.

### What does NOT transfer — clock/quarter assumptions to strip out

Everything below is genuinely sport-with-a-clock-shaped and must NOT be reused or ported for tennis; a new tennis-specific engine module is correct, not a missed reuse opportunity:

- `ep-model.js`'s `CLOCK_STOPPAGE_TRIGGERS`/`CLOCK_RESTART_EVENTS`/`CLOCK_DELTA_CAP`/`PLAY_QTR_SECONDS`/`PLAY_GAME_SECONDS` — AFL's stoppage-adjusted quarter clock has no tennis analog; tennis has no elapsed-time state at all in its win-probability inputs, only point/game/set *counts*.
- `wp-model.js`'s `time_remaining`, `game_seconds`, `period_seconds`, `is_second_half`, `is_extra_time`, `footballTimeInHalfRemaining`'s per-half "sawtooth" clock, and the whole `time_scaling`/`match_seconds_cap` (regulation vs. extra-time denominator) machinery — all built around a fixed-duration match with a countdown clock. Tennis has no match-length cap (a five-setter can run indefinitely) and no clock-remaining feature; the Markov recursion's "time" axis is purely discrete score-state, not seconds.
- `live-wp-calibration.js`'s `aflMinsRemaining()` — a minutes-remaining proxy used only to weight a leverage term; tennis's leverage (how much a point matters) is a function of score-state (break point, set point, deuce) not clock position, so this needs a genuinely different (score-state-based) leverage formula if the tennis design wants one at all.
- `score-tracker.js`'s `attachAflScores`/`attachFootballScores` running-score-from-event-stream logic, and `ep-model.js`/`football-spadl.js`'s "chain"/possession event-sequence model (`chain_number`, `chain_action_num`, per-action credit splitting) — these exist because AFL/football's live models need shot-by-shot/action-by-action state built from a raw event feed. Tennis's win-probability recursion needs only the current point/game/set score, which is a vastly simpler live-state object than a possession chain; no event-stream flattening or per-action credit-splitting analog is needed for the win-prob number itself (though a future point-by-point momentum/shot-quality feature, if ever wanted, would need its own tennis-specific event model — out of scope here).
- The `EXPECTED_FEATURES_*` feature-drift-detection pattern in `ep-model.js`/`wp-model.js` exists specifically because a retrained XGBoost model's tree splits can silently reference a renamed/dropped feature. It has no tennis analog because there's no tree structure to drift — the parameter blob's few named scalars are validated the simpler way `live-wp-calibration.js` already does it (a `SUPPORTED_FORMS` allow-list + finite-number checks + identity fallback), not a per-feature allow-list.

### Summary spec (deliverable)

1. **Live-model artifact**: `tennis/live-params.json` (or per-match `tennis/live-params/{matchId}.json`) on R2 bucket `inthegame-data`, published via a one-off `wrangler r2 object put --remote` from wherever the Bayesian layer runs (no new CI needed — same manual-publish precedent as `afl/wp-model-chain.json`/`afl/live-wp-calibration.json`). Format: flat JSON, versioned `form` field, ~5-10 numeric serve/return parameters per player. Size: low hundreds of KB for a full-slate file, under 1 KB for a per-match file — smaller than any existing XGBoost model artifact in this repo.
2. **Fast layer**: a new `worker/src/tennis-engine.js` (or client-side equivalent JS module) implementing the point→game→set→match closed-form/DP recursion (~50-100 lines including the loader), using the same module-scope R2-cache-once and never-throw-fallback discipline as `live-wp-calibration.js`. No XGBoost, no `_xgb-runtime.js` dependency, no tree JSON.
3. **Live loop**: reuse `live-poller.js` and `live-badge.js` completely unmodified via `sport`/`prefix` config.
4. **Worker registration**: add `/tennis/live-scores` (+ any per-match detail endpoint) to the plain if-chain router in `worker/src/index.js`; no `wrangler.toml` changes beyond a cron slot if a scheduled feed-refresh is wanted (budget is tight: 5/5 free-tier slots used).
5. **Static path**: a new `{tennis-data-repo}/build-blog-data.yml` publishing `tennis/*.parquet` to the same R2 bucket, mirroring torpdata/pannadata/bouncerdata, for rankings/GOAT/career pages — independent of the live-model artifact.
6. **Site registration**: new `tennis/` `.qmd` directory + `tennis/CLAUDE.md`, `_quarto.yml` navbar block, `docs/reference/MODELS.md` row (flagging that its "XGBoost" wording needs a footnote/loosening for a legitimately non-ML live model), optionally render-excluded/nav-commented at first using the cricket precedent for a beta launch.
7. **Blocker check**: none found in the existing plumbing. The two-speed, no-ML-runtime design is fully supported by the current architecture and is simpler to integrate than the XGBoost pattern football/AFL use, because `live-wp-calibration.js` already establishes "small JSON blob + closed-form JS arithmetic, loaded once per isolate, fail-open to identity" as a proven, production pattern in this exact Worker. The only genuine open question this ticket does not resolve is where the live tennis *score feed* itself comes from (covered by tickets 02/03), which this delivery pattern is agnostic to — whatever score-state the feed provides, the recursion consumes it the same way.
